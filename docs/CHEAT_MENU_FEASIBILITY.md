# 作弊菜单可行性分析（2026-10-21）

> 这是实现前的历史离线分析。后续已完成F1开放、中文字体及原生输入路径验证，当前实现和边界见[NATIVE_CHEAT_MENU.md](NATIVE_CHEAT_MENU.md)；下文“本轮仅分析”描述当时状态，不代表当前构建。

## 结论

**可以实现，而且当前Steam程序已经包含完整的原生调试菜单，优先复用它，比从头注入另一个GUI更合适。**
本轮仅离线分析；没有制作、安装或执行作弊补丁，没有启动游戏或读写存档。

Ghidra分析FUN_14004f890确认以下项目实际参与GUI调用，并非只检出孤立英文字符串：

|菜单项目|静态确认内容|

|Unlimited Ammo|同一字段bit10，mask0x400；武器发射路径据此跳过扣弹|

## 真实游戏逻辑交叉核查

- FUN_140147c90在现有弹药非零、武器可以射击时执行发射动作；0x400关闭时才对打包弹药字段减1。
- FUN_140143740的另一武器路径同样在0x400关闭时减弹。另定位到多个0x400读取点，不能仅凭其中两条路径就宣称每种武器、换弹、投掷物全部实机通过。
- **无限弹药不等于从0生成弹药**：至少一个路径先判断已有弹药，再判断是否跳过消耗。首版宜配合一次补满弹药动作，再分别核查弹匣、备弹和消耗品。
- FUN_1401098b0会读取0x200，并改变角色生命状态写入时的分支/限幅。菜单确有原生无敌开关，但环境伤害、毒、剧情死亡和各首领路径仍需实际场景验证；本报告不把静态标志位等同于全流程不死验收。
- 作弊位所在数据与存档银行邻近/处于原生复制范围，不能承诺原生开关“绝不写入存档”或“退出自动清零”；后续实现必须单独检查存读档、新游戏和切关的生命周期。

## 开启入口与输入

- 菜单显示状态为DAT_1404a2f1d，允许开启状态为DAT_1404a2f1c。
- FUN_14004f890读取输入对象+0x22c的上升沿；只有允许位开启（或菜单本来已打开）时才切换显示状态。
- FUN_1401a7c50将内部键码0x7e写入该输入位。内部键码不是直接的Win32虚拟键，不将0x7e猜成某个F键。
- FUN_14013caa0包含内部按钮序列`TTSSLRLRST`；完成序列会翻转允许位，并调用音效入口。T/S/L/R对应的实际键盘/手柄映射、触发界面仍须进一步定位和实机确认；这不是已经验证可直接输入的操作说明。
- `/saves/debug.json`确实被读取，但FUN_14004edc0只确认序列化MainVsync、MuteMusic、MuteSfx、ShowSectionName；未见它读写上述作弊位或菜单允许位。不能凭文件名直接建议给debug.json添加GodMode等虚构键。

## 中文菜单所需工作

现有调试UI与汉化正文使用不同字体。初始化明确只收集ASCII32–126，Tuffy字体也不是当前中文正文的Fusion字库。
所以仅将Invulnerable改成“无限生命”会造成调试UI缺字，仍需补充中文字体及实际所需glyph范围，或复用游戏原生中文UI控件。

推荐首版边界：

1. 保留现有汉化；提供一个明确的菜单开关/快捷键，无需输入内部秘密序列。
2. 复用原生无敌和无限弹药位；先做“无敌、无限弹药、恢复生命”三个独立开关/按钮，默认关闭。
3. 完成中文字体与鼠标/键盘输入焦点处理；确认关闭菜单后不会吞掉移动/射击。
4. 对新旧存档副本、切场景、死亡重试、各武器空弹/换弹做验收，再决定是否增加全武器等项目。
5. 发行只包含版本/字节守卫的小型差分或独立可卸载组件；不分发完整原EXE，不把作弊强制混进普通汉化安装。

独立实现时保持其他状态位的最小操作原则：
```cpp
// 设计示意，不是已注入游戏的代码。
flags = enabled ? (flags | feature_mask) : (flags & ~feature_mask);
// Invulnerable: feature_mask=0x200; Unlimited Ammo: feature_mask=0x400.
```

## 资源层替代路线

全3471成员、317个小型文本配置（含300个CONFIG INI）审计发现708个生命/伤害/弹药相关键。
MaxAmmo/MaxClipAmmo和拾取量可以调有限容量，但不是无限弹药；将敌伤改零也不能保证覆盖所有环境/脚本伤害。
资源配置未发现现成的作弊菜单开关。此负面结论仅限资源配置，不能否定上文已确认的EXE菜单。
