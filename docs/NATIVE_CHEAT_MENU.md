# 原生作弊菜单（2026-10-21）

## 使用

安装本轮完整包后，按 **F1** 打开或关闭原生菜单，鼠标操作复选框和按钮；也可用原生方向/确认输入导航。菜单关闭后，无敌、无限弹药等已勾选状态继续生效，再次打开可取消。

菜单完整保留：无限生命、无限弹药、恢复生命、全部/单件武器、全部/单件物品、清除敌人、角色死亡、任务目标、完成任务、章节跳转、区域载入、界面/武器/小地图隐藏、成就重置，以及原生环境、雾效、光照、声音和同步设置。中文数据共86项，调试字体包含278个所需字符。

复选框是持续开关；获得物品、杀敌、跳关、重置成就等原生按钮执行一次操作，不是可撤销的开关。原生菜单把有些按钮限定为游玩中执行：标题画面可以打开菜单，但没有玩家/关卡时仍保留原生可用性检查。无限弹药原生逻辑是“不扣除已有弹药”，零弹药时需先取得武器/弹药。

## 已验证的实现

- 输入翻译器 `FUN_1402dd940`：Win32 `VK_F1=0x70` 转为内部键码`0x1c`；原快捷键V转为`0x7e`。
- `0x1401a7d4b`：`83 fa 7e` → `83 fa 1c`，只改变调试菜单的内部键码比较。
- `0x14004fa49`：`75 04` → `eb 04`，绕过隐藏解锁条件，保留按下沿、长按去抖、开关状态和窗口关闭行为。
- 原生可见状态`0x1404a2f1d`仍控制鼠标捕获分支及游戏操作屏蔽。隔离CPU回放验证这些实际机器码片段；没有注入轮询线程或新增窗口钩子。
- 原生无敌/无限弹药仍使用游戏对象`+0x40a4`的`0x200/0x400`。回调、武器逻辑、任务操作和存档逻辑保持原实现。
- `.locmenu`为新增的只读、不可执行PE节。53个原生调试字符串/字形范围RIP引用重定向；35个物品/武器及7个区域组名称指针沿用已有DIR64重定位，兼容ASLR。
- 原调试字体`TUFFY_BOLD.TTF`仅由原生调试初始化载入。本轮使用已锁定Fusion字体的确定性字符子集替代，并同时扩充原ASCII字形范围；不是仅换字体后遗漏字符范围。
- 所有地址是已锁定版本的首选VA，不是可跨版本复用的固定运行时地址。

## 光标显示后点击和滚动失效的修正（2026-10-22）

**已验证根因**：平台鼠标消息函数`FUN_1402f5350`在窗口`+0x7a`、`+0x79`之后还检查`+0x19`捕获请求。上一修正为显示/释放系统光标把`+0x19`清零，却遗漏了这条消息门禁，导致`WM_MOUSEMOVE`和鼠标按下/松开都直接返回。菜单指针坐标停在刚打开时的中心；即使滚轮已到ImGui `+0x140`，目标菜单也未被实际悬停。REA证据`ev_fae6c3e72854c413d73074aa8b65686a3bbceed7ee5e1ceaa3bb10f175dcfcd6`及逐指令回放一致。

`tests/test_menu_pointer_dispatch.py`从实际平台消息函数开始，串联原生排队回调、原生队列分发`0x1a86a0`、输入对象方法`0x2ed60`、原菜单IO拷贝，以及实际ImGui `UpdateMouseInputs`、悬停窗口选择和`UpdateMouseWheel`。断言点击边沿、长按不重复、松开边沿、悬停窗口和真正的菜单滚动目标变化，而非只断言补丁自己写入的字段。旧构建重现坐标停在`960,540`且滚动目标为零；修正后首选基址及`0x180000000`重定位共6项通过。失焦/关闭分支仍阻断原先受捕获门禁保护的事件。此为离线机器码回放；真实窗口交互仍单独验收。

## 能移动但实际按钮未触发：完整帧按钮状态修正（2026-10-22）

**已验证根因**：上项消息修复后，原生排队点击已到输入对象；但原生`UpdateInput`在绘制调试菜单之前，用游戏捕获/原始输入合成结果覆盖`input+0x231/+0x232`（RVA`0x2f5a8`、`0x2f5af`）。菜单拥有系统鼠标时该游戏结果为中立，实际`DrawDebugMenu`读到的按键又变为零。此前回放在排队事件后直接调用ImGui消费者，遗漏了中间这次覆盖；只看到`MouseClicked`字段和悬停并不能证明真实按钮已触发。

新补丁在RVA`0x2f5a8`对7个源字节做守卫，仅菜单可见时跳过这两个游戏合成写入。原生排队点击仍是唯一鼠标按钮来源，正常游戏的合成写入原样执行。关闭或失焦清除输入时还调用原生ImGui `ClearActiveID`（`0x66e70`，参数`0,0`），取消未完成的按住状态，避免重开/重获焦点后旧按住被当成新的松开点击。

## 实际注册WndProc仍吞掉每次点击：外层捕获门禁（2026-10-22）

用户继续确认：鼠标长按一秒再松开也没有响应，但键盘菜单可用。因此同帧合并短按/松开的推测不是本次实际故障解释，未加入点击锁存或触摸/笔消息过滤修改。

**已验证根因**：实际注册的Win32窗口过程`0x2f3650`先进入外层`0x2f3900`，并非旧夹具作为起点的公共翻译器`0x2de7a0`。外层在`0x2f39cc`处理鼠标按下时检查窗口`+0x19`。菜单为显示指针保持该字段为零，于是每次按下都进入`0x2f39d2`：重新捕获鼠标、调用`0x2f34d0`，随后直接返回，**没有把本次按下交给公共消息翻译器**。每帧菜单光标逻辑又释放捕获，所以下一次按下继续被当作“首次点击捕获”吞掉。移动消息走另一分支，故指针能移动并不代表按下到达。

修正仅在原生菜单可见时绕过这一个外层重新捕获分支：对RVA`0x2f39cc`原6字节`44 38 73 19 75 11`守卫，相对跳转至`.locui+0xa00`，然后重入`0x2f39e3`，**仍执行原生窗口`+0x7a/+0x79`焦点检查**。菜单关闭时原比较、首次点击捕获并消耗该点击的行为保持不变。原生输入构造/启动实测`+0x218/+0x219/+0x21a=1/1/1`，不是输入开关未开启；没有据此改动这些原生模式字段。

`tests/test_menu_message_path.py`从实际输入构造、启动移动开关和回调注册开始，经过真正注册WndProc，复现旧构建按下被`capture-and-discard`分支吞掉；修正后按下到达队列且捕获字段保持零，菜单失焦仍阻断，普通游戏首次点击捕获仍保留。

`tests/test_menu_full_frame.py`进一步串联该注册WndProc、原生队列、引擎轮询、原菜单IO拷贝、完整原生ImGui `NewFrame`（含导航、悬停和`MouseDownOwned`）、原生`Begin`、**完整原生`Checkbox`**、`End`及`EndFrame`。上下文和窗口均由实际原生构造代码生成，不手填ActiveId或所有权字段；CRT分配/内存/数学、TLS窗口单例及Win32调用使用明确边界替身，字体仅最小元数据而不做画面验收。首选/ASLR基址都覆盖60帧按住后一松开及连续两次完整点击：旧8dce构建全部失败；修正后鼠标所有权为1、`NavDisableMouseHover=0`，实际复选框依次开启/关闭。该回放仍区别于真实Windows鼠标输入和游戏内可见操作验收。
